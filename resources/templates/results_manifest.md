# Template: results manifest

The file that answers *"which run produced this number?"* — for every figure, table, and headline claim in a paper.

**The test it exists to pass.** Hand someone only the PDF: can they find the code? Hand them only the repository: can they find the paper? Both answers should be yes. In practice this is the most commonly skipped step in computational research, and it costs nothing at the time and a great deal later.

**When you need one.** Always, but especially when code and manuscript live in separate repositories, when results were produced on a cluster, or when anyone other than you will ever have to defend a number.

**Where it goes.** `results/MANIFEST.md` in the code repository, with a copy or a link in the manuscript repository. See [`../practices/scientific_figures_tables.md`](../practices/scientific_figures_tables.md) §5 and [`../practices/private_code_to_public_package.md`](../practices/private_code_to_public_package.md) §9.

## The template

```markdown
# Results manifest — <paper short title>

Every figure, table, and quantitative claim in the manuscript, and what produced it.

- **Code:** <https://github.com/org/repo> at `<tag or commit>`
- **Manuscript:** <repo or DOI>
- **Production run:** `results/<run-id>/` — see the run record below
- **Last verified:** <YYYY-MM-DD> by <who>

## Figures

| Figure | Script | Config | Input data | Output | Notes |
|---|---|---|---|---|---|
| 1 | `scripts/make_fig1.py` | — | `data/processed/survey.csv` | `results/<run>/fig1.pdf` | schematic; no computation |
| 2 | `scripts/run_sweep.py` → `scripts/make_fig2.py` | `configs/base.yaml` | `data/processed/batch3.csv` | `results/<run>/fig2.pdf` | |
| 3 | `scripts/make_fig3.py` | `configs/highT.yaml` | `results/<run>/sweep.csv` | `results/<run>/fig3.pdf` | seeds in config |

## Tables

| Table | Generated by | Source data | Notes |
|---|---|---|---|
| 1 | `scripts/make_table1.py` | `results/<run>/metrics.csv` | formatting only; no computation |
| 2 | hand-written | — | parameter definitions, not results |

## Quantitative claims in the text

<Every number in the abstract, results, and conclusions that is not in a
figure or table.>

| Claim | Location | Value | Source |
|---|---|---|---|
| cost reduction | Abstract, §4.2 | 17% | `results/<run>/summary.csv`, row `cost_delta` |
| speedup | §4.3 | 5.2× | `results/<run>/timing.csv` |
| "approximately doubles" | §5 | — | **UNTRACED — resolve before submission** |

## Run record — `<run-id>`

- **Date:** <YYYY-MM-DD>
- **Code commit:** `<full hash>`  (working tree clean: yes/no)
- **Command:** `<exact command line, including flags>`
- **Config:** `configs/<file>` (sha256 `<hash>`)
- **Input data:** `<file>` (sha256 `<hash>`)
- **Seeds:** `<value(s)>`
- **Environment:** `<environment.yml / lockfile>`; Python `<x.y.z>`;
  `<solver/library>` `<version>`
- **Hardware / runtime:** <machine, wall time — matters for anything expensive>

## Superseded and invalid runs

<Quarantine rather than delete: a directory renamed with its reason is better
documentation than any note, and deleting the run that produced a number leaves
the claim without its working.>

| Run | Status | Why |
|---|---|---|
| `results/20260814_v1/` | superseded | isotherm fit corrected; see log 2026-08-14 |
| `results/20260802_invalid_seed/` | invalid | seed collision across replicates |

## Data availability statement (for the manuscript)

<Draft it here so it stays in sync with what is actually true.>

> Code and data are available at <URL> (version `<tag>`, DOI `<10.xxxx/zenodo.xxxxx>`).
> Figures 2–5 and Tables 1–2 can be reproduced with `<command>`; see `results/MANIFEST.md`.
```

## Machine-readable variant

If you'd rather have it parseable — for a check script, or because the manifest is generated — the same content as YAML:

```yaml
paper: "<short title>"
code_repository: "https://github.com/org/repo"
code_commit: "<full hash>"
archive_doi: "10.5281/zenodo.xxxxxxx"

figures:
  fig2:
    script: scripts/run_sweep.py
    config: configs/base.yaml
    inputs: [data/processed/batch3.csv]
    output: results/20260827_prod/fig2.pdf
    seeds: [20260705]
  fig3:
    script: scripts/make_fig3.py
    config: configs/highT.yaml
    inputs: [results/20260827_prod/sweep.csv]
    output: results/20260827_prod/fig3.pdf

claims:
  - text: "costs decrease by 17%"
    location: "Abstract; §4.2"
    source: results/20260827_prod/summary.csv#cost_delta
    status: verified
  - text: "approximately doubles"
    location: "§5"
    source: null
    status: cannot_verify        # a real, useful answer — do not guess one
```

Keep `status: cannot_verify` as a legitimate value. An untraced claim you have *recorded* as untraced is a problem you can fix before a reviewer finds it; one you have quietly filled in with a plausible source is worse than either.

## Filling it in without hating it

**Let the figures record themselves.** If you save figures with [`../scripts/figure_style/`](../scripts/figure_style/), each one already writes a `.provenance.json` next to it containing the script, commit, sources, and library versions. The manifest table then becomes a summary of files you already have rather than something you reconstruct by memory.

**Hash the inputs, don't describe them.** `sha256` of the config and data files takes one command and settles arguments that prose cannot:

```bash
shasum -a 256 configs/base.yaml data/processed/batch3.csv
```

**Write the run record when you launch the run**, not when you write the paper. At launch you know the command, the commit, and the seeds; three months later you are guessing.

**Fill the claims table last, from the manuscript.** Read the abstract and results sections, list every number, then find its source. Whatever you cannot trace in ten minutes is exactly what a reviewer will ask about — mark it `UNTRACED` and deal with it now.

## Using it with an AI assistant

**Build the first draft from the repository:**

> Read `templates/results_manifest.md`. Draft `results/MANIFEST.md` for this repository: for each figure referenced in `manuscript/`, determine which script and data file produced it, and which commit. Use the `.provenance.json` sidecars where they exist. Where the link genuinely isn't recorded, write `cannot determine` — do not infer a plausible source. Report how many you traced and how many you could not.

**Then audit the claims, which is the part that finds problems:**

> Following `practices/manuscript_audit.md` §4, list every quantitative claim in the abstract, results, and conclusions. For each, find the results file that should support it and check the value. Produce the claims table from `templates/results_manifest.md` with a status of `verified`, `mismatch`, or `cannot verify`. Recompute independently from the data rather than calling the analysis code. Change nothing.

**Keep it honest afterwards:**

> Check `results/MANIFEST.md` against the repository: flag any script, config, or output path that no longer exists, and any figure in `manuscript/figures/` that the manifest doesn't mention.

That last one is worth running before every submission. Manifests rot the same way every other living document does — the fix is the same as everywhere else in these practices: give the rule something that fails.
